# 20 · المحوّلات

> كيف يتصل المنتج بأي مصدر. هذه الوثيقة تحدد الإطار، لا تفاصيل كل محوّل. تفاصيل محوّل PeopleSoft في [10-peoplesoft-notes.md](10-peoplesoft-notes.md).

## العقد

كل محوّل ينفّذ منفذًا واحدًا ([src/adapters/ports.ts](../src/adapters/ports.ts)):

```ts
interface StudentDataSource {
  id: SourceId;
  manifest: AdapterManifest;                       // النسخة 1: تصريح ثابت بالقدرات والفئة
  sync(ctx: SourceContext): Promise<SyncResult>;   // قراءة واحدة، بالنموذج الموحّد
}

interface AdapterManifest {
  tier: 'A' | 'B' | 'C' | 'D';                     // انظر الفئات أدناه
  provides: DataArea[];                            // ما يقدّمه: الجدول، والحضور، والدرجات…
  credentials: 'none' | 'token' | 'password';      // ما يحتاجه من الطالب
  maintainer: string;                              // من يصونه
}
```

**قواعد العقد:**

1. **المحوّل يقرأ فقط.** لا يوجد في العقد ما يكتب، ولن يوجد.
2. **المحوّل لا يعرف الواجهة،** والواجهة لا تعرف المحوّل. يلتقيان في النموذج الموحّد ([07-data-model.md](07-data-model.md)).
3. **المجال الذي لا يقدّمه المحوّل يختفي من الواجهة بهدوء.** لا شاشات فارغة ولا رسائل خطأ.
4. **فشل مجال لا يمحو بياناته القديمة.** يبقى آخر ما عُرف، مع وقته.

## الفئات: حسب المخاطرة

| الفئة | المصدر | بيانات الدخول | أين يعمل | المخاطرة |
|---|---|---|---|---|
| **أ** | ملف: Excel، أو CSV، أو Google Sheets منشور، أو تقويم ics، أو JSON بقالبنا | لا شيء | المتصفح وحده | معدومة |
| **ب** | واجهة رسمية: واجهة المؤسسة حسب [عقد التكامل](11-integration-contract.md)، أو معيار OneRoster، أو الواجهات الرسمية لمنصات التعلّم (Moodle، وCanvas، وBlackboard) | رمز (Token) يصدره المصدر للطالب | المتصفح، وأحيانًا الحافة | منخفضة: المصدر نفسه صمّم الواجهة للتطبيقات |
| **ج** | جسر صغير **تستضيفه المؤسسة** يقرأ من قاعدة بياناتها (MongoDB أو PostgreSQL أو غيرها) ويطبّق عقد التكامل | ما تقرره المؤسسة | خادم المؤسسة | منخفضة: المؤسسة تملكه وتتحكم فيه |
| **د** | قراءة صفحات النظام بكلمة مرور الطالب، مثل PeopleSoft وBanner | كلمة المرور | الحافة (رعد) | **الأعلى.** يُستخدم فقط حين لا يوجد غيره |

**لماذا لا يتصل المتصفح بقاعدة البيانات مباشرة؟** لأن بيانات الدخول إلى القاعدة ستكون داخل الموقع، فيراها كل من يفتحه، ويقرأ بيانات كل الطلاب. القاعدة تُقرأ دائمًا عبر جسر (الفئة ج) يعرض لكل طالب بياناته فقط.

### شروط إضافية للفئة د

- قائمة صفحات مسموحة، وجلسة معزولة لاكتشاف أي صفحة جديدة.
- حماية الحافة: حدود الطلبات، وإيقاف الرقم بعد محاولات خاطئة ([09-security-privacy.md](09-security-privacy.md)).
- تعريف صريح بالمشروع في كل طلب، وسلوك مهذب مع المصدر.
- **إشعار المؤسسة قبل النشر الواسع،** والتوقف فورًا إذا طلبت.
- مراجعة أمنية لكل تعديل، لأن كلمات المرور تمر عبره.

## شروط قبول أي محوّل

- [ ] ينجح في **اختبارات المطابقة** كاملة.
- [ ] يصرّح بقدراته وفئته وصائنه في `manifest`.
- [ ] لا يخزّن بيانات الطلاب على أي خادم.
- [ ] عيّناته في الاختبارات **وهمية أو مُجهّلة بالكامل**.
- [ ] للفئة د: الشروط الإضافية أعلاه.

## المعايير التي نبني عليها

لا نخترع العقد وحدنا. النموذج الموحّد يُربط بمعيارين مفتوحين، فيعمل أي مصدر يطبّقهما دون محوّل خاص به.

| مفهومنا | المعيار |
|---|---|
| الفصل | OneRoster: `academicSession` |
| المادة والشعبة | OneRoster: `course` و`class` |
| تسجيل الطالب في الشعبة | OneRoster: `enrollment` |
| الدرجة | OneRoster: `result` (الإصدار 1.2) |
| المحاضرة والاختبار | iCalendar: `VEVENT` |
| الحضور، والحرمان، والقيود، والمطلوب | **لا يغطيها المعياران**، فهي امتدادات خاصة بنا |

التفاصيل الدقيقة تُكتب عند بناء أول محوّل من الفئة أ أو ب، في النسخة 2.

## كيف يُضاف محوّل (مختصر)

1. مجلد جديد في `src/adapters/<id>/`.
2. `manifest` بالقدرات والفئة والصائن.
3. عيّنات وهمية أو مُجهّلة في `test/fixtures/<id>/`.
4. تشغيل اختبارات المطابقة حتى تنجح كلها.
5. ملف مؤسسة يشير إلى المحوّل.
